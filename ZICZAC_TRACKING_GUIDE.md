# ZicZac verified prediction tracking

ZicZac now separates first **pre-kickoff** forecasts from **independently
verified** regulation-time final scores. This does not guarantee exact-score
accuracy or produce scores for fixtures whose data are unavailable.

## What is automatically collected

The existing GitHub **Capture verified pre-match evidence** workflow checks
published provider data on its configured schedule and preserves:
- Earliest saved original website predictions from `data/prematch/snapshots/`.
- Frozen research forecasts (v8, v8_near, v9, v10) in
  `data/v10_prospective/forecasts/`.
- Each actually returned individual AI score in frozen
  `data/llm_research/forecasts/` (not an invented six-provider consensus).
- All five original combinations in write-once
  `data/v10_prospective/doubles/` selections.

The consolidated *public-data-only* audit lives in
`data/tracking/status.json`. It is also generated by the independent
**Publish ZicZac Verified Prediction Audit** workflow. That audit makes **no
sports API or LLM calls**, and these workflows are not a workaround for an
exhausted provider quota.

## Private website forecasts

The Deep Research and Ten-AI **Run** buttons and the AI Five-Double **Run**
button now attempt to save original returned scores in a separate,
append-only PostgreSQL table, `ziczac_interactive_forecasts`.

To enable durable private captures:
1. Configure `ZICZAC_ACCESS_PASSWORD` in **Streamlit Cloud → App → Settings
   → Secrets**, and sign in to ZicZac. Never put this password in GitHub code.
2. Configure a working **PostgreSQL** `DATABASE_URL` in Streamlit Secrets.
   GitHub Actions secrets cannot automatically be read by Streamlit.
3. Open **Performance → All Predictions → Check all saved prediction results**.
   The dashboard will merge private DB originals with automatically frozen
   GitHub evidence for the signed-in owner only.
4. Check the confirmation after running on-demand research. **"NOT centrally
   saved" means that forecast is session-only and cannot be guaranteed to
   survive a Streamlit restart.** Fix the database or login before relying on
   historical result tracking.

GitHub's public audit deliberately **does not upload your private PostgreSQL
predictions, private AI votes or private five-double selections**.

## What does HIT, MISS, or PENDING mean?

- **HIT:** An independently verified full-time regulation score exactly
  matches the original frozen score, or one of the original five double options
  matches **both** completed fixtures.
- **MISS:** A verified regulation-time result differs from the frozen score;
  for a five-double set, neither of the five original combinations matched
  both completed results.
- **PENDING:** The matching final score is not yet verified, a match was
  postponed, source identity is uncertain, or access to provider results is
  temporarily unavailable. **Pending does not mean loss.**
- Legacy predictions without sufficient original source IDs/kickoff are
  preserved but excluded from measured hit rates.

Full-time results are accepted only when the provider, fixture ID, both team
IDs, original kickoff, regulation-time score and post-kickoff verification
match. Historical replays and edits after kickoff never count as wins.

## Ask for an update

Ask ChatGPT **"Check my latest ZicZac verified exact-score and five-double
results"**. ChatGPT can inspect the public
`data/tracking/status.json` report in GitHub. To inspect **private**
per-match on-demand results, sign in to the Streamlit **Performance** screen
and refresh the tracker; those records are not exposed through the public
repository.

Six providers are tracked individually **only when they return valid
pre-match scores**. A missing/blocked Gemini, Claude, Grok, etc. response is
not an automatic missed prediction. If no independently verified final
results are available, the report shows **no measured hit rate** instead of
claiming either 0% or 100% accuracy.

## Durability and privacy

- Historical scheduled prediction files are write-once in GitHub.
- Private on-demand predictions use first-write-wins in PostgreSQL; a later
  rerun cannot overwrite the original source/fixture/method selection.
- No provider API keys, password, prompt bodies or authorization headers are
  written to prediction records.
- Incomplete data and API quota failures are reported honestly. No unsafe
  retries, fabricated scores or retroactive reclassification as an original.
